Gate logic revision — client-approved 2026-09-26

Four changes were proposed to the client (Saqib Jawed) and approved ("Approve all 4"). Implemented as two separate modules — scripts/gate_old.py (unmodified original rule, kept for comparison) and scripts/gate_new.py (revised rule) — so every result can report both columns side by side. See reports/gate_comparison_chart.html for the visual comparison.

1. MONITORING status

n < min_n, ROI > 0, CI crosses zero, but CI width < 40 points (disclosed threshold, not tuned after seeing results) → MONITORING instead of FAIL. Re-check cadence (how often, max checks before a final verdict) is an operational scheduling decision the client is still finalizing — not encoded in gate_new(), which only classifies a single snapshot.

2. Point-in-time feature audit

Process requirement, not a numeric rule: any new feature must document the exact date range it draws from relative to the game being predicted, before it's used in a gate-relevant model. Directly motivated by three real leakage bugs found this session (see Bugs).

3. CLV tracked, report-only

gate_new() accepts an optional clv_positive_rate that's carried through in the result detail for visibility — it never affects the PASS/MONITORING/FAIL verdict.

4. Power-derived min_n

derive_min_n() in gate_new.py implements the calculation, but no market-specific thresholds have actually been computed/approved yet — every result in this report still uses the default n=500. Real open follow-up, not silently done.

Handling disagreeing re-checks (new this round)

Two results this round update the project's established precedent for what to do when a more rigorous re-check disagrees with an earlier, simpler result.

When the stronger test agrees more (pitcher_strikeouts)

Untuned logistic regression: +2.24% ROI. CV-AUC-tuned XGBoost on the identical pool: +4.98% ROI, genuinely better CV-AUC (0.60-0.66). The stronger test found a stronger signal — real evidence the line-movement lead is getting sharper, not an artifact.

When the stronger test disagrees (batter_runs_scored)

Untuned logistic regression: +2.79% ROI. CV-AUC-tuned XGBoost: -10.33% ROI, despite equally solid CV-AUC (0.65-0.67). Per this project's own established precedent (Addendum 47 vs 30, Addendum 51 vs 30, Addendum 53 vs 55c — the more rigorous re-check has always been treated as authoritative when they disagree), this MONITORING status should be read as contested and weak, not confirmed. A separate hurdle-model decomposition (Addendum 88) independently landed at a decisive FAIL (n=38,081, CI entirely negative), consistent with the tuned re-check rather than the original untuned one.

Real bugs found & fixed this session

Documented so nobody re-discovers these the hard way. Two are pre-existing/upstream (not introduced this session) and were worked around per-script rather than patched at the source — flagged below as a recommended follow-up.

  • Join-fan-out on duplicate game_pk (Addendum 37) — merging onto a table with duplicate keys, twice, compounds row inflation multiplicatively. Caused spurious 0.95–0.997 AUCs before being caught by a row-count sanity check. Now a mandatory pattern in every new script this session: print row counts before/after every merge.
  • Pre-existing duplicate-game_date-per-game_pk in boxscore (13+ instances, root-caused to inconsistent source data, not this project's code) — cascades into the canonical build_team_game_log() producing 4,547 rows for only 3,845 unique games. Recommended follow-up: fix at the source in xgboost_individual_markets.build_team_game_log() so every future addendum doesn't need its own workaround.
  • Timezone date-bucketing bug (event discovery, Addendum 48/phase1) — date_trunc('day', commence_time) on a TIMESTAMPTZ column truncates in the DB session's local timezone (+05:00 here), not UTC — caused ~54% of event-discovery queries to target the wrong calendar day. Fixed by explicit AT TIME ZONE 'UTC' before truncating.
  • Doubleheader event-ID collision (event discovery) — matching by team-pair alone silently assigned the same real event_id to both games of a doubleheader. Fixed by matching on team-pair + closest commence_time, consuming each candidate event once. 35 residual collisions after the fix were dropped rather than debugged further (cheap to lose ~70 rows vs. chasing an edge case).
  • Unnecessary dropna on partial features (Addendum 48) — a new script required every one of 22 enrichment features non-null before using a row, silently discarding an entire new season (2026, zero cache_mlb_historical_pitcher_statcast coverage) that XGBoost's missing=np.nan config was already designed to handle. Removed — recovered most of the fuller game log's real benefit.
  • Post-game snapshot leakage in cache_odds_snapshots (Addendum 56/56b) — this table keeps recording price snapshots well after game start (84%+ of picks have their "latest" snapshot 10-12+ hours post-game-time, likely settled/archived prices). Using the naive "latest snapshot" as the closing line leaks the outcome into the feature and produced a spurious mechanical PASS for h2h (CI entirely positive, WR 89%) that vanished once filtered to snapshot_time <= game_time. Any future use of this table must apply that filter before aggregating.
  • Season-aggregate starter-quality leakage (Addendum 68, discovered via h2h EDA) — cache_mlb_historical_pitcher_statcast is keyed only by (player_id, season): one row per pitcher per season, that pitcher's FINAL, whole-season ERA/xERA/xBA, applied identically to every start he made that year — including starts before the season ended. This feature (add_starter_game_features/add_opp_pitcher_features in addendum37_historical_enrichment.py) was used project-wide: h2h, totals, pitcher_outs, and batter_strikeouts all inherited it. Confirmed via a controlled comparison: the leaked feature correlated with h2h's actual outcome at r=-0.185; the corrected, genuinely point-in-time replacement (build_starter_rolling_era, Addendum 68) correlates at r=-0.011, not significant. No verdict flipped once fixed (all four markets still FAIL) but every number using this feature before Addendum 68 should be considered unreliable.
  • Two fan-out bugs in the batter_runs_scored pipeline (Addendum 62) — (1) build_team_game_log()'s game log has 3,858 rows for only 3,845 unique game_pk (the same class of bug documented in Addendum 37 for a different pipeline, never fixed here); (2) NEWLY FOUND: client_games has 8,678 unique event_id but only 7,029 unique game_pk — multiple event rows per real game — which silently inflated the park-factor join and, through it, the whole pool by ~27% (156,848→211,922 rows). The originally published Addendum 30 baseline (n=52,981) was computed on this fanned-out data. Corrected reproduction: n=5,953 (not 52,981), ROI=-2.63% (not -2.54%) — same verdict, different (trustworthy) numbers.
  • Market key naming mismatches in cache_odds_snapshots (Addendum 60) — pitcher props use short-form keys (pitcher_k, not pitcher_strikeouts) while batter props use full names (batter_runs_scored matched directly, no mismatch). A first query for pitcher_strikeouts returned zero rows and would have been wrongly reported as "no data" without checking the table's actual distinct market values. Always confirm the exact market key via a sample query before concluding a table has no coverage. Confirmed this session: batter_strikeouts genuinely has no key at all in this table (checked directly) — not a naming mismatch, real absence.
  • XGBoost/GridSearchCV walk-forward results are seed-unstable in this environment (Addendum 72 stability check) — re-running Addendum 49's basic h2h feature set (elo/l10/fatigue only, pre-dating the later leak fixes/enrichment) across 8 different random seeds produced 4/8 PASS, 4/8 FAIL, ROI ranging from -2.38% to +2.25% (mean -0.03%). A single run's exact PASS/FAIL is not trustworthy in isolation for this feature set — the true underlying edge is close enough to zero that which random seed you happen to use decides the verdict. This does not change h2h's overall status: the FAIL verdict is independently supported by 6+ later, richer-feature architectures (market-offset GLM, clustering, joint Poisson, EBM, platoon features) that all converge on the same small-negative/no-edge conclusion regardless of seed, plus a null CLV result. If anything, this finding reinforces why this project treats convergence across independent methods as the real evidence, not any single run's number. Practical implication going forward: never trust a single walk-forward run's exact PASS/FAIL near the decision boundary — multi-seed stability (or the equivalent: multiple independent architectures agreeing) is required before reporting a verdict as solid.
